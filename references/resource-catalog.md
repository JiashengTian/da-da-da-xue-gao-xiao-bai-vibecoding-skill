# 可借鉴资源目录

这是调研的起点，不是默认依赖清单。每次使用前打开官方页面或仓库核验版本、许可证、费用、维护状态和是否适合当前项目；外部图片、图标和模板也要检查各自许可。不要把用户的密钥、真实数据或受版权保护素材提交到任何示例项目。

## 1. 找到合适的画面和操作方式

| 资源 | 适合借鉴什么 | 正确使用方式 |
| --- | --- | --- |
| [Mobbin](https://mobbin.com/) | 常见 App 页面、登录、搜索、结账流程 | 只分析页面结构、信息顺序和交互，不复制品牌、文案或素材。 |
| [Page Flows](https://pageflows.com/) | 一个功能从开始到结束的完整操作路线 | 比较“用户先看到什么、每步点什么、失败时怎样恢复”。 |
| [Awwwards](https://www.awwwards.com/) | 具有鲜明视觉风格的网站 | 适合找视觉方向，不适合照抄复杂动效或牺牲可读性。 |
| [Dribbble](https://dribbble.com/) / [Behance](https://www.behance.net/) | 颜色、排版、卡片、插画的灵感 | 把灵感转成自己的布局和品牌语言，不能把展示图当作可商用素材。 |
| 用户提供的截图或链接 | 用户明确喜欢与不喜欢的地方 | 逐项问“喜欢的是颜色、结构、按钮还是操作步骤”，不要复制原产品。 |

先做“灵感拆解表”：参考链接、喜欢的具体点、不采用的点、适合本项目的改法。至少找 2 个不同来源，避免整套设计像单一产品的复制品。

## 2. 网站和 App 的基础界面

| 资源 | 适合何时使用 | 使用前要查 |
| --- | --- | --- |
| [shadcn/ui](https://ui.shadcn.com/) | 希望界面可自由调整、需要常见表单/对话框/菜单 | 安装方式、当前框架兼容性、组件无障碍说明；只安装会用到的组件。 |
| [Radix Primitives](https://www.radix-ui.com/primitives) | 需要可靠的弹窗、菜单、选择器、提示等底层交互 | 当前框架、样式工作量和可访问性行为。 |
| [MUI](https://mui.com/) | 想快速做成熟的后台、表格、表单或企业工具界面 | 主题定制难度、包大小、需要的组件是否有免费版本。 |
| [Tailwind CSS](https://tailwindcss.com/) | 想高效定制视觉，并且项目已有或适合使用它 | 项目是否已使用它；不要为了一个按钮引入整套新方案。 |
| [Storybook](https://storybook.js.org/) | 页面或组件很多，需要逐个看外观并防止改坏 | 当前项目是否支持；把它当作检查工具，不替代真实使用测试。 |

同一个项目优先选择一套主界面体系。混用多个大组件库容易让按钮、间距和交互看起来不像同一个产品。

## 3. 图标、字体、图片和插画

| 资源 | 适合何时使用 | 注意 |
| --- | --- | --- |
| [Lucide](https://lucide.dev/) | 需要统一、清晰的常用功能图标 | 图标必须配合可理解的按钮标签或提示；核对当前包的许可证。 |
| [Heroicons](https://heroicons.com/) | 使用 Tailwind 生态或需要简洁图标 | 保持同一套图标风格和大小。 |
| [Iconify](https://iconify.design/) | 需要很多图标来源 | 每个图标集可能有不同许可证，不能只看 Iconify 平台许可。 |
| [Google Fonts](https://fonts.google.com/) | 寻找可读字体 | 每个字体家族单独检查许可证；中文界面要确认汉字覆盖与加载速度。 |
| [Unsplash](https://unsplash.com/license) / [Pexels](https://www.pexels.com/license/) | 需要临时或通用照片 | 阅读当前许可；避免拿人物照片暗示真实客户、治疗效果或商品背书。 |
| [unDraw](https://undraw.co/illustrations) | 需要可换颜色的简单插画 | 先检查许可和项目风格是否匹配，别用插画遮盖主要操作。 |

优先使用用户自己的品牌资料、可证明许可的素材或生成图片。所有图片需要有替代文字；纯装饰图片可标为装饰，关键内容不能只放在图片里。

## 4. 动效、拖拽、节点图和特殊视觉效果

| 资源 | 适合何时使用 | 需要问用户 |
| --- | --- | --- |
| [Motion](https://motion.dev/) | 页面切换、展开收起、轻量反馈动效 | 动效是为了提示状态还是只是好看？能否关闭或减少？低性能设备是否流畅？ |
| [Lottie](https://lottiefiles.com/) | 成功、加载、空状态等小动画 | 动画文件的来源/许可、文件大小、是否影响首屏。 |
| [React Flow](https://reactflow.dev/) | 流程图、节点编辑器、拖拽画布 | 用户是否真的需要编辑节点；简单展示可用静态图或普通列表。 |
| [CSS-Tricks](https://css-tricks.com/) | 搜索 CSS 视觉效果的实现思路 | 仅作学习和原型参考，检查文章日期与当前浏览器兼容性。 |

“液态玻璃”“毛玻璃”“3D”等效果先做一个小原型，在真实手机和电脑上检查文字是否清楚、按钮能否点击、滚动是否顺畅。视觉效果不能妨碍内容、性能和无障碍。

## 5. 表单、表格、搜索和数据展示

| 资源 | 适合何时使用 | 注意 |
| --- | --- | --- |
| [React Hook Form](https://react-hook-form.com/) | 表单多、需要清晰校验和错误提示 | 用户看到的是人话提示，不是技术错误码。 |
| [Zod](https://zod.dev/) | 需要统一检查用户填写内容 | 不要只在前端检查，服务端也要校验。 |
| [TanStack Table](https://tanstack.com/table) | 复杂表格、排序、筛选、分页 | 先确认用户是否真的需要表格；手机上通常要改成卡片或重点字段。 |
| [Recharts](https://recharts.org/) / [Apache ECharts](https://echarts.apache.org/) | 趋势、对比、统计图 | 图表必须回答一个问题；没有数据时写清楚原因，不造假数据。 |
| [Algolia](https://www.algolia.com/) | 大量内容的站内搜索 | 先说明服务费用、索引的数据和隐私；小数据量不必过早引入。 |

先用一份真实感的假数据验证“用户看得懂吗”，再连接真实数据。图表、搜索和筛选是容易膨胀的功能，第一版只保留一个最有价值的视角。

## 6. 登录、保存数据、文件、付款和第三方能力

| 能力 | 候选起点 | 先向用户说明 |
| --- | --- | --- |
| 登录与云端保存 | [Supabase](https://supabase.com/docs)、[Firebase](https://firebase.google.com/docs) | 账号从哪里来、数据保存在哪里、免费额度和费用、删除账号/数据怎么办。 |
| 仅个人使用的保存 | 浏览器本地保存或简单文件 | 换设备或清除浏览器后会怎样；是否需要备份或云端同步。 |
| 文件上传 | 当前后端/存储服务的官方文档 | 允许的类型和大小、病毒扫描、隐私、谁能下载、删除期限。 |
| 在线付款 | [Stripe](https://docs.stripe.com/) 等正式支付服务 | 国家/地区、企业/税务要求、退款、手续费和不得自行处理银行卡信息。 |
| 地图和位置 | [MapLibre](https://maplibre.org/)、地图提供商官方文档 | 地图费用、位置权限、地理数据来源和不授权时的替代方式。 |
| 邮件/短信/推送 | 对应供应商的官方文档 | 谁会收到、何时发送、退订、费用和失败重试。 |

只有主要用户路线真的需要时才加登录、付款、上传或定位。它们会增加账号、隐私、安全、费用和客服责任。原型阶段用模拟数据，未经用户确认和安全检查不要连真实账户或付款。

## 7. 质量检查与发布

| 资源 | 用来做什么 | 小白可理解的说法 |
| --- | --- | --- |
| [Playwright](https://playwright.dev/) | 自动走一遍关键操作路线 | “让程序自己反复点一遍，确认关键步骤没被改坏。” |
| [axe-core](https://github.com/dequelabs/axe-core) | 发现部分无障碍问题 | “帮我们找出键盘、文字和提示可能让人用不起来的地方。” |
| [Lighthouse](https://developer.chrome.com/docs/lighthouse/) | 检查网页性能、基础无障碍和最佳实践 | “检查网页打开速度和明显问题，不替代真人试用。” |
| [W3C WAI](https://www.w3.org/WAI/fundamentals/accessibility-intro/) | 无障碍基础参考 | 把可读、可点、可键盘操作、错误可恢复作为最低要求。 |
| [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) | 安全检查方向 | 重点防止密码、私人资料和支付信息被错误处理。 |
| [OpenSSF Scorecard](https://scorecard.dev/) | 了解开源依赖的安全维护信号 | 仅作信号；仍要核验许可证、版本和本项目风险。 |

发布前在真实手机和电脑上走一遍最重要路线。用户自己试用时，问“你会点哪里”和“哪里不懂”，不要在旁边解释到他能完成为止。

## 9. 明确不要做的事

- 不从截图、Dribbble、竞品页面或付费模板直接抄图片、文字、品牌、代码或完整布局。
- 不因为 GitHub 星标高就跳过许可证、维护、兼容性和安全检查。
- 不往小项目堆入多个 UI 库、动画库、状态库和后端服务；每引入一项都要说明它解决的明确问题。
- 不为了“看起来很酷”加入导致文字难读、加载很慢或手机难用的效果。
- 不在客户端代码、截图、提交记录或聊天中暴露密钥、密码、真实客户资料或付款信息。
